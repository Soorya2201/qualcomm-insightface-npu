Snapdragon Access Vision - Possible Optimisations
==================================================

Current state
-------------

Both CavaFace and DINO configurations target 40 FPS:

    frame_interval_ms = 25.0

The webcam requests 40 FPS. The adaptive browser loop adds no fixed delay when
processing exceeds the 25 ms frame budget, and it does not build an unbounded
queue of stale frames.

Measured locally on the Snapdragon X Elite NPU with the current float models:

    Stage                         Mean latency    Approximate ceiling
    YOLOv5-Face                   83.5 ms         12 FPS
    CavaFace per face             10.8 ms         93 FPS
    Complete one-face inference   94.3 ms         10.6 FPS

The browser can capture at 40 FPS, but the current pipeline processes roughly
10 FPS. The primary bottleneck is the current unoptimised float YOLO model, not
cosine matching or CavaFace.

1. Export YOLOv5-Face through Qualcomm AI Hub Workbench
--------------------------------------------------------

The current YOLO is a generic float ONNX with NCHW input. Its raw local QNN
call takes approximately 76.6 ms. Qualcomm reports approximately 4.65 ms for a
Workbench-optimised YOLOv5-Face on Snapdragon X Elite, so replacing this model
has the highest expected impact.

Use a Workbench-produced ONNX or, preferably, precompiled_qnn_onnx. A
precompiled QNN ONNX embeds a device-specific QNN context and avoids expensive
graph preparation during application startup.

Reference:
https://huggingface.co/qualcomm/YoloV5-Face

2. Quantise YOLO, but benchmark float and W8A16
------------------------------------------------

Test these candidates rather than assuming quantisation is always faster:

    - Optimised float ONNX as the accuracy baseline
    - W8A16 as the first quantised candidate
    - W8A8 only after accuracy evaluation

Published Snapdragon X Elite figures include approximately:

    YOLO artifact       Published latency
    QNN DLC float       4.654 ms
    QNN DLC W8A16       5.046 ms
    ONNX W8A16          14.571 ms

Quantisation reduces model size and can improve performance, but latency is
model- and runtime-dependent. Profile each candidate. Use 500-1000
representative, unlabeled calibration frames containing both cameras,
different lighting, near and distant faces, front and side poses, empty scenes,
and multiple faces.

Reference:
https://workbench.aihub.qualcomm.com/docs/hub/quantize_examples.html

3. Keep CavaFace float initially
--------------------------------

CavaFace is not the main bottleneck. Qualcomm reports about 4.32 ms NPU
inference on Snapdragon X Elite; the measured 10.8 ms includes Python
preprocessing and output normalisation.

Reference:
https://huggingface.co/qualcomm/CavaFace

W8A16 CavaFace can be evaluated later, but embeddings are sensitive to
quantisation. After changing the embedder:

    1. Regenerate all enrolled embeddings.
    2. Recalculate genuine and impostor cosine distributions.
    3. Select a new cosine threshold.
    4. Check front and side-angle accuracy.

Never reuse embeddings generated by a different embedding model or precision.

4. Add temporal tracking and identity caching
-----------------------------------------------

Detection and identity inference do not need to run on every displayed frame.
A better 40 FPS design is:

    40 FPS video rendering
        -> YOLO every 3-4 frames
        -> track bounding boxes between detections
        -> embed once when a track appears
        -> refresh identity every 0.5-1 second

This keeps the displayed video smooth while avoiding repeated inference on the
same face.

5. Reduce CPU preprocessing and frame-copy overhead
----------------------------------------------------

The current NumPy path resizes 640x480 to 640x640, converts uint8 to float32,
normalises it, transposes HWC to NCHW, and transfers approximately 1.23 MB of
raw RGBA through localhost for every frame.

Evaluate a channel-last Workbench model with quantised uint8 I/O. Relevant
Workbench options include:

    --force_channel_last_input image
    --quantize_io

The application already detects NCHW versus NHWC model shapes, but model input
and output names must match the exported artifact.

6. Use a precompiled QNN context for deployment
------------------------------------------------

The runtime currently uses burst performance mode and requires the NPU, which
is appropriate. Context caching can improve subsequent startup time but will
not materially improve steady-state FPS. A Workbench precompiled_qnn_onnx
artifact is the preferred deployment target for Windows on Snapdragon.

7. Use GenieX for event-level generative reasoning
---------------------------------------------------

GenieX is a runtime for generative LLMs and VLMs; it is not the runtime for
YOLO or face-embedding ONNX models. Keep deterministic authorization in the
YOLO plus face-embedding pipeline.

Use GenieX asynchronously only when an unauthorized event occurs:

    YOLO + face embedder
        -> deterministic authorization
        -> unknown-person event
        -> send one snapshot to a local GenieX VLM
        -> produce an incident description or correlate observations
           from camera 1 and camera 2

Do not run a VLM on every frame. It would contend with the vision models for
NPU resources and harm real-time performance.

GenieX exposes an OpenAI-compatible local server at http://127.0.0.1:18181.
For GenieX model precision, use a Qualcomm QAIRT model bundle for the strongest
NPU path. For GGUF, Q4_0 is the recommended Hexagon NPU format; Q8 and F16
generally use GPU or CPU.

References:
https://geniex.aihub.qualcomm.com/en/get-started/what-is-geniex
https://geniex.aihub.qualcomm.com/en/run/cli/local-server
https://geniex.aihub.qualcomm.com/en/models/supported

Recommended implementation order
--------------------------------

    1. Workbench-optimise and profile YOLOv5-Face.
    2. Compare float, W8A16, and possibly W8A8 detector accuracy and latency.
    3. Add bounding-box tracking and identity caching.
    4. Keep the face embedder float until YOLO is solved.
    5. Add GenieX asynchronously for unauthorized-event explanations.
    6. Quantise the face embedder only after collecting a verification dataset.
